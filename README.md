# SkillGap

SkillGap — бот в MAX для девятиклассников, которые уже рассматривают программы среднего профессионального образования. По региону, коду программы и квалификации бот показывает возможные стартовые должности, анализирует актуальные вакансии «Работы России» и осторожно сопоставляет требования рынка с федеральной примерной образовательной программой или ФГОС.

Бот не выбирает профессию за пользователя и не гарантирует трудоустройство. `work_roles` и `vacancy_queries` — поисковая модель, а не официальный перечень профессий.

## Проблема и ценность MVP

Приоритетный пользователь — девятиклассник, который уже рассматривает конкретную программу СПО и хочет проверить её применительно к своему региону. Без SkillGap ему приходится отдельно искать программу и квалификацию в федеральном справочнике, вручную просматривать вакансии, сравнивать разные формулировки требований и самостоятельно оценивать зарплатную выборку. Эти источники не дают готового ответа о связи выбранной программы с текущим стартовым рынком.

SkillGap собирает этот узкий сценарий в MAX: пользователь задаёт регион и программу, а бот возвращает возможные направления работы, воспроизводимую выборку вакансий, требования работодателей, осторожный Skill Gap по федеральному документу и PDF со ссылками. Полезный результат — не рекомендация профессии, а проверяемая отправная точка для разговора с родителями, колледжем или работодателем.

Актуальность решения подтверждается самим наличием раздельных официальных источников — федерального каталога/ПОП/ФГОС и открытых вакансий «Работы России». Продуктовая гипотеза состоит в том, что единый короткий сценарий уменьшит ручной поиск и сделает происхождение выводов понятным. Это гипотеза MVP, а не уже доказанный эффект.

## Пилот, метрики и масштабирование

Первый безопасный пилот — один проверенный пользовательский сценарий на вручную проверенных поисковых моделях каталога (`SKILLGAP_CATALOG_POLICY=pilot`) с доступом к выбору любого региона. Для пилота достаточно бота, PostgreSQL, живой интеграции с «Работой России» и доступных федеральных документов; владельцы процесса — команда продукта и эксперт, проверяющий связи «программа → стартовые роли → запросы».

Обезличенные метрики пилота уже предусмотрены: прохождение этапов воронки до доставленного отчёта, длительность и исход анализа, режим данных `live/cache/test`, ошибки доставки и оценка результата 👍/👎. Предварительные целевые ориентиры для принятия решения о расширении: не менее 70% завершений начатого выбора, не менее 80% успешных доставок отчёта, p95 анализа до 90 секунд и не менее 70% положительных оценок среди ответивших. Это цели пилота; репозиторий не выдаёт их за достигнутые показатели.

Расширение выполняется поэтапно:

1. Экспертно проверить новые поисковые модели и перевести политику с `pilot` на `current`, затем при готовности — на `all`.
2. Сохранить неизменными сценарий, модель данных и интерфейс MAX; адаптировать региональные запросы, документы и роли без создания отдельного продукта для каждого региона.
3. При росте нагрузки вынести задания анализа в внешнюю устойчивую очередь и общий кэш, после чего масштабировать экземпляры приложения горизонтально.
4. После успешного пилота согласовать владельцев справочника, регламент повторной проверки ссылок/моделей и периодичность оценки качества выдачи.

## Основной сценарий

1. Пользователь открывает бота в MAX и нажимает «Выбрать направление».
2. Выбирает регион кнопкой или вводит его название.
3. Вводит код СПО, например `09.02.11`, или часть названия.
4. При необходимости выбирает квалификацию и запускает анализ.
5. Получает статистику в чате и PDF с карточками вакансий, навыками, зарплатой при её наличии, датой выборки и прямыми ссылками на источник.
6. Для частых навыков из вакансий видит статусы «Найдено», «Частично найдено» или «Не найдено в анализируемом документе» и подтверждающие фрагменты ПОП/ФГОС там, где совпадение найдено.

Кнопка «Начать заново» доступна в актуальных сообщениях. `/privacy` объясняет работу с данными, `/forget` удаляет сохранённый выбор.

## Архитектура

```text
MAX -> POST /webhook -> PostgreSQL (durable inbox) -> webhook workers -> bot.Handler
bot.Handler <-> PostgreSQL (bot_sessions) -> каталог СПО -> очередь анализа
очередь анализа -> «Работа России» + утверждённая ПОП/ФГОС -> статистика + PDF -> MAX
```

Проект состоит из одного Go-процесса, мигратора и PostgreSQL. Сценарий бота живёт в `internal/bot`, каталог — в `internal/catalog`, адаптер вакансий — в `internal/vacancies`, безопасный разбор федеральных документов — в `internal/skillgap`, PDF — в `internal/pdfreport`, MAX API — в `internal/maxapi`. Подробности и честный перечень ограничений — в [`docs/architecture.md`](docs/architecture.md).

Живые HTTP-маршруты:

- `POST /webhook` — webhook MAX, требует `X-Max-Bot-Api-Secret`;
- `GET /healthz` — liveness процесса;
- `GET /readyz` — готовность принимать трафик;
- `GET /metrics` — метрики Prometheus.

Отдельного клиентского REST API в проекте нет.

## Быстрый запуск

Требуются Docker 24+ с Compose v2, бот из кабинета MAX и публичный HTTPS-адрес для production webhook.

1. Создайте локальный env-файл:

   ```bash
   cp .env.example .env
   ```

2. Замените в `.env` все значения `replace_me_*`. Пароль PostgreSQL должен быть длинным и URL-safe; не используйте реальные секреты из примера.

3. Запустите весь обязательный контур одной командой:

   ```bash
   docker compose up -d --build
   ```

Миграции выполняются автоматически. Готовность:

```bash
curl --fail http://127.0.0.1:8080/readyz
docker compose ps
```

Приложение намеренно публикуется только на `127.0.0.1:8080`. В production разместите перед ним reverse proxy с доверенным TLS-сертификатом. `MAX_WEBHOOK_URL` должен быть публичным `https://.../webhook`; бот оформляет подписку при старте и повторно подтверждает её каждые 30 минут, чтобы восстановиться после автоматической отписки MAX при длительной недоступности webhook.

Для host Nginx используйте [`deploy/nginx/skillgap.locations.conf.example`](deploy/nginx/skillgap.locations.conf.example): скопируйте его в каталог snippets, подключите через `include` внутри уже настроенного HTTPS `server`-блока, затем выполните `nginx -t` и reload. Пример отправляет на `127.0.0.1:8080` только точный `/webhook`, возвращает 404 на остальные публичные пути и разрешает health/metrics лишь с loopback. TLS-сертификат и сам `server`-блок намеренно остаются ответственностью владельца домена.

## Параметры окружения

| Переменная | Обязательна | Назначение |
|---|---:|---|
| `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB` | да | PostgreSQL в Compose |
| `DATABASE_URL` | вне Compose | DSN PostgreSQL; в Compose собирается автоматически |
| `MAX_BOT_TOKEN` | да | Токен бота MAX, только в `Authorization` |
| `MAX_WEBHOOK_SECRET` | да | Секрет заголовка webhook, 5–256 символов `A-Z a-z 0-9 _ -` |
| `MAX_WEBHOOK_URL` | production | Публичный HTTPS URL webhook |
| `MAX_WEBHOOK_RECONCILE_INTERVAL` | нет | Период повторного подтверждения подписки MAX, по умолчанию `30m` |
| `MAX_WEBHOOK_MAX_BODY_BYTES` | нет | Максимальный размер webhook, по умолчанию 1 MiB |
| `SKILLGAP_CATALOG_PATH` | нет | Путь к каталогу; в образе `/app/spo_program_vacancy_map.json` |
| `SKILLGAP_CATALOG_POLICY` | нет | `all`, `current` или `pilot`; безопасное значение по умолчанию — `pilot` |
| `TRUDVSEM_BASE_URL` | нет | Endpoint вакансий; только точный официальный URL из `.env.example` помечается как live-источник «Работа России»; любой другой URL — test |
| `TRUDVSEM_*` | нет | Таймаут, размер ответа, RPS и число страниц |
| `SKILLGAP_ANALYSIS_*` | нет | Таймаут, воркеры и очередь анализа |
| `SKILLGAP_VACANCY_CACHE_MAX_BYTES` | нет | Максимум памяти кэша рыночных срезов, по умолчанию 32 MiB |
| `SKILLGAP_SESSION_TTL` | нет | Срок хранения выбора региона/программы, по умолчанию 24 часа |
| `SKILLGAP_DOCUMENT_*` | нет | Таймаут, кэш и лимиты безопасного разбора ПОП/ФГОС |
| `SKILLGAP_MAX_*`, `SKILLGAP_QUERY_*` | нет | Границы поиска и PDF |
| `SKILLGAP_EVENT_*` | нет | Воркеры, recovery, retry, лимит попыток (по умолчанию 8) и TTL надёжной очереди webhook |
| `GRAFANA_PASSWORD` | для observability | Пароль локальной Grafana |
| `COMPOSE_PROFILES` | production opt-in | `observability`, если Prometheus/Grafana должны запускаться и обновляться при deploy |

Все настройки запуска приложения и Compose с безопасными значениями по умолчанию перечислены в [`.env.example`](.env.example). Тестовые opt-in переменные находятся рядом с соответствующими тестами; секреты не коммитятся.

По умолчанию включена политика `pilot`: она оставляет только актуальные программы с проверенной (`ProductionReady`/curated) поисковой моделью. Политика `all` сохраняет поиск по всем 610 кодам, но её нужно включать явно; предварительные поисковые модели при этом помечаются пользователю как требующие проверки. `current` скрывает исторические программы. Неизвестное значение политики безопасно заменяется на `pilot`.

## Как строится выборка

- Поиск идёт по запросам выбранной программы и региону, после чего вакансии дедуплицируются и ранжируются по релевантности.
- Отсеиваются senior/lead/руководящие позиции, обязательное высшее образование и другие hard negatives.
- Опыт показывается раздельно: «без опыта», «до года» и «не указан».
- Зарплатные агрегаты строятся в одной доминирующей валюте, диапазон преобразуется в середину; медиана и диапазон не показываются при менее пяти наблюдениях.
- Рядом с выводом указываются источник, время и часовой пояс, режим `live/cache/test`, размер выборки и этапы её фильтрации.

## Как строится Skill Gap

- Навыки для сопоставления берутся только из найденных вакансий, а не придумываются по названию профессии.
- Для программы используется только утверждённая федеральная ПОП. Если её нет, недоступна или формат нельзя разобрать, применяется действующий ФГОС; неутверждённый проект ПОП источником не считается.
- Анализатор принимает PDF, DOCX и ZIP с DOCX, скачивает документы только по HTTPS с разрешённого федерального хоста и ограничивает размер, число страниц и содержимое архивов.
- Для каждого навыка показывается осторожный статус: «Найдено», «Частично найдено» или «Не найдено в анализируемом документе». Для найденного совпадения приводится короткий фрагмент и, когда доступно, страница, раздел или файл.
- В PDF фиксируются вид федерального документа, прямая ссылка, время получения и SHA-256 содержимого. Документы кэшируются в памяти процесса на 30 минут; кэш не переживает рестарт.
- «Не найдено» означает только отсутствие совпадения в автоматически разобранном федеральном документе. Это не утверждение о программе конкретного колледжа и не гарантия уровня подготовки выпускника.

## Пошаговая проверка

Перед проверкой убедитесь, что `/readyz` отвечает 200, а `docker compose logs app` содержит строки о подключении к PostgreSQL, загрузке каталога, авторизации бота и подписке webhook.

1. Отправьте `/start`.
2. Нажмите «Выбрать направление».
3. Выберите «Москва».
4. Введите тестовый код `09.02.11`.
5. Выберите программу и квалификацию, если бот предложит выбор.
6. Нажмите «Анализировать» и дождитесь завершения.
7. Проверьте, что в чат пришла статистика, а затем PDF. В PDF должны быть дата и режим данных, число вакансий, навыки, зарплаты и кликабельные ссылки. Если зарплата не указана, ожидаемо «Нет данных».
8. Если федеральный документ доступен для автоматического разбора, проверьте раздел Skill Gap: у навыков есть осторожные статусы, а у найденных совпадений — фрагменты; в PDF указаны URL документа, время получения и SHA-256. При недоступном или неподдерживаемом документе ожидается явное предупреждение, а не выдуманный результат.
9. Нажмите «Начать заново» и убедитесь, что выбор сброшен.
10. Отправьте `/privacy`, затем `/forget` и убедитесь, что бот подтвердил удаление сохранённого выбора.

Живая выдача зависит от состояния внешнего источника и может меняться между запусками.

## Разработка и проверки

Для локальной Go-разработки нужен Go 1.26 и [Task](https://taskfile.dev/):

```bash
task verify       # vet, lint, race/coverage tests, govulncheck и сборка
task test         # быстрые юнит-тесты
task test-coverage # отчёт о покрытии в coverage.out
task compose      # валидация Compose на .env.example
task build        # сборка production-образа
```

Обычные тесты детерминированы и используют явно синтетические fixtures; PostgreSQL integration-тест включается в CI через `TEST_DATABASE_URL`. Живые smoke-тесты внешних источников намеренно opt-in, чтобы недоступность стороннего сервиса не делала CI случайно красным:

```bash
TRUDVSEM_LIVE_TEST=1 go test ./internal/vacancies -run TestLive
SKILLGAP_LIVE_DOCUMENT_URL='https://spolab.firpo.ru/...' \
  go test ./internal/skillgap -run TestLive
```

Для просмотра метрик:

```bash
docker compose --profile observability up -d
```

Перед включением профиля задайте в `.env` сильный `GRAFANA_PASSWORD`; защитная проверка не позволит запустить Grafana с пустым или шаблонным паролем. Для постоянного production opt-in добавьте `COMPOSE_PROFILES=observability`: тогда deploy обновляет и эти сервисы. Без opt-in deploy явно останавливает и удаляет старые контейнеры Prometheus/Grafana, оставшиеся от прежней обязательной конфигурации, но сохраняет их volumes. Grafana и Prometheus публикуются только на localhost. В Grafana автоматически добавляются Prometheus и dashboard `SkillGap Overview` с воронкой, исходами и временем анализа, оценкой полезности и доступностью. Они не входят в обязательный контур.

## Остановка, перезапуск и логи

```bash
docker compose restart app
docker compose logs -f app
docker compose --profile observability down
```

Команда с профилем останавливает и основной контур, и опциональные Prometheus/Grafana; она безопасна, даже если профиль не запускался. PostgreSQL volume сохраняется. Безвозвратное удаление локальных данных выполняется только явной командой `docker compose --profile observability down --volumes`.

## CI/CD

Pull request и push в `main`/`master` проходят formatting check, `go vet`, lint, race/coverage tests, `govulncheck`, поиск секретов/уязвимостей, валидацию полного Compose-профиля и Prometheus, сборку образа и smoke-test мигратора. Проверенный образ экспортируется как артефакт с SHA-256 и при deploy загружается на сервер без повторной сборки, поэтому в production запускается именно просканированный образ этого commit SHA. Deploy создаёт каталог релиза и ожидает `/readyz`. Для релиза без новых миграций при ошибке автоматически поднимается предыдущая версия и отдельно проверяется её готовность. Перед изменением схемы workflow гарантированно запускает существующую БД и создаёт AES-256-зашифрованный `pg_dump` в `/opt/max-bot/backups`; если backup получить нельзя, релиз останавливается до миграции. Автооткат бинарника при изменившейся схеме намеренно не выполняется.

Нужны GitHub Secrets: `SERVER_HOST`, `SERVER_USER` и `SERVER_SSH_KEY`. SHA-256 fingerprint production-сервера закреплён в workflow; при ротации host key его нужно отдельно сверить и обновить в коде. На сервере должны быть Docker с Compose v2.20+, Bash, OpenSSL, curl, `diff`, `find`, `grep` и GNU coreutils, а также существовать `/opt/max-bot/.env`; workflow не копирует и не выводит этот файл. При первой резервной копии workflow атомарно создаёт `/opt/max-bot/secrets/backup-encryption.key` с правами `0600`. Если ключ пропал, но зашифрованные backup остались, deploy остановится и не заменит ключ молча. Копию этого ключа нужно хранить во внешнем защищённом хранилище: без него backup восстановить нельзя.

После успешного deploy зашифрованные backup, каталоги старых релизов и неиспользуемые образы SkillGap старше 30 дней удаляются. Текущий и непосредственно предыдущий каталог релиза сохраняются независимо от возраста.

Проверяйте восстановление на отдельной БД, не поверх production. На сервере из каталога текущего релиза:

```bash
cd /opt/max-bot/current
sha256sum -c /opt/max-bot/backups/before-COMMIT_SHA.dump.enc.sha256
docker compose -p max-bot --env-file /opt/max-bot/.env exec -T db \
  sh -c 'createdb --username="$POSTGRES_USER" skillgap_restore_check'
openssl enc -d -aes-256-cbc -pbkdf2 -iter 200000 \
  -pass file:/opt/max-bot/secrets/backup-encryption.key \
  -in /opt/max-bot/backups/before-COMMIT_SHA.dump.enc | \
docker compose -p max-bot --env-file /opt/max-bot/.env exec -T db \
  sh -c 'pg_restore --exit-on-error --no-owner --username="$POSTGRES_USER" --dbname=skillgap_restore_check'
docker compose -p max-bot --env-file /opt/max-bot/.env exec -T db \
  sh -c 'dropdb --username="$POSTGRES_USER" skillgap_restore_check'
```

Замените `COMMIT_SHA` на имя нужного файла. Workflow создаёт рядом SHA-256 checksum для обнаружения случайной порчи. AES-256-CBC защищает конфиденциальность backup, но эта незаверенная checksum не защищает от целевой подмены обоих файлов и не заменяет регулярный restore drill; переносите резервную копию и checksum в защищённое backup-хранилище.

## Приватность и безопасность

- Токен MAX и webhook-secret хранятся только во внешнем `.env`/хранилище секретов.
- Лицензии и обязательные уведомления библиотек, включённых в бинарники, собраны в `THIRD_PARTY_NOTICES` и копируются в production-образ. Лицензию самого проекта должен отдельно выбрать владелец.
- Webhook принимается только с корректным `X-Max-Bot-Api-Secret`.
- Корневые сертификаты Минцифры проверяются по SHA-256 при сборке. При их легитимной ротации новые хэши нужно сверить с официальным источником и отдельно обновить `Dockerfile`.
- Готовые PDF и полная история диалога отдельно не сохраняются. Для продолжения после рестарта PostgreSQL хранит `chat_id`, ограниченное навигационное состояние и до подтверждения доставки — подготовленный ответ вместе с адресными полями. Сразу после успешной доставки содержимое и адресные поля ответа очищаются, остаётся только технический ключ события и статус. Через 24 часа запись перестаёт восстанавливаться и удаляется при следующем цикле очистки; команда `/forget` удаляет её сразу.
- Для надёжной доставки PostgreSQL временно хранит исходный webhook payload (в том числе текст, если он был в событии). Сразу после успешной обработки payload и текст очищаются; для дедупликации остаются технические `chat_id`, ключ/тип события и статус. Завершённые записи удаляются через 30 дней, неуспешные с payload для retry — через 7 дней; TTL настраивается. Доступ к PostgreSQL должен быть ограничен, backup — зашифрован.
- Штатные логи не содержат текстов сообщений, callback payload, IP-адресов, `chat_id`, `user_id`, `message_id` или `callback_id`. Ошибка разбора `DATABASE_URL` журналируется без исходного DSN; для диагностики остаются стадия, тип события, номер попытки и безопасные агрегаты.
- Не размещайте в открытом доступе `/metrics`, Grafana, PostgreSQL и порт приложения. Снаружи нужен только HTTPS `/webhook` и, при необходимости, защищённые health checks.

Проект ориентирован на несовершеннолетних, поэтому не следует добавлять сбор лишних персональных данных, профилирование или публичную историю запросов.

## Ограничения

- Сопоставление идёт по тексту федеральной ПОП/ФГОС, а не по рабочей программе конкретного колледжа. Оно помогает найти упоминания, но не измеряет качество или глубину обучения.
- Сканированные PDF без текстового слоя не распознаются: OCR не выполняется. RAR не поддерживается; если в RAR была ПОП и доступен ФГОС, бот честно использует ФГОС, иначе сообщает, что вывод сформировать нельзя.
- Статус «Частично найдено» основан на консервативном совпадении связанных формулировок, поэтому результат остаётся вспомогательным и требует содержательной проверки человеком.
- Каталог связывает код с возможными должностями для поиска; это не гарантия трудоустройства.
- Часть поисковых моделей требует ручной проверки; это помечено в каталоге.
- Навыки рынка извлекаются из текста и структурированных полей вакансий; автоматическое извлечение может быть неполным.
- Зарплата рассчитывается только по вакансиям, где она указана, и не является прогнозом заработка конкретного выпускника.
- Задача анализа живёт в памяти процесса. Если процесс перезапущен во время анализа, сохранённый выбор восстанавливается, а анализ можно безопасно запустить повторно.
- Живой отчёт зависит от MAX и «Работы России». После успешного запроса в памяти есть stale-cache до 24 часов с явной отметкой режима; после рестарта или без предыдущей выборки при недоступности источника возможен отказ.
